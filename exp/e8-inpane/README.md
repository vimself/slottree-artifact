## 2. 协议要点

- **为什么这样改**：问题只在「扫描 → 索引」这一侧——扫描的代价随窗格里的事件数平方增长，晚一个窗格反应就可能付出整窗格的二次方；「索引 → 扫描」晚一个窗格只多付 O(n log n)，所以切回仍只在边界判，滞回（2c 对 c）与 EWMA 不动。窗格内用本窗格的累计平均、不用 EWMA：EWMA 要到窗格结束才更新，第一个窗格的 s̄ 恒为 0，正是 E5 的症结
- **B = 1024 怎么定的**（看计时数据之前，只看了数据的事件分布）：检查本身每事件一次取模加一次比较；每个窗格最多触发一次建树（O(n log n)，与窗格边界切换同价）；触发前最多多扫 B 个事件。真实数据里每组每窗格的事件数最多：WPI 202 / 265（留出 / 开发）、PAMAP2 275、Nasdaq 5、公交 22、Porto 20、METR-LA 1、Intel Lab 36，只有 Binance 到 4,319（133 个（组, 窗格）≥ 1,024，s = 10 s 里的成交突发）⇒ 除 Binance 外，v2 在全部真实数据上检查都不触发，决策与 v1 逐事件相同（闸 (e) 在 W = 10 分 COUNT 上逐份核）；E1 / E2 / E4 / E6 / E7 的重跑主要是回归检查，E5 是修法真正起作用的地方
- **与 v1 的 diff**（`python3 -I tests/diff_v1.py` 逐块列出，并检查改动只落在允许的块里）：`ArmM` 三处（成员 `inpane`、`n_inpane`；`init` 多一个参数 B；`process` 的代价规则块里加检查）；驱动五处（`Opt` 的 `--inpane`、`Result` 与 `run_arm` / `run_arm_lat` 带出窗格内切换次数、`dispatch` 传 B、`main` 解析参数与输出 `inpane_switches` 行）；文件头注释。OPP、`Scan`、`ScanC`、`Tree`、A1、`Fin` 逐字不变
- **计时口径的两处细节**：D 取 v1 表的值（v1 的 D 由 OPP 与 M 的探测遍取小的定；若重新探测，OPP 在 Binance 上每行要 100 s 以上，且 M 变快后 D 可能变，同一行 v1 / v2 就不是同一条流）；「进程 → 臂」的交错只在重跑的臂（M、A2）之间，别的臂不陪跑
- **为什么 (i) 用 v1 的 A4**：论文的图表从同构的 v2 表出，表里的 A4 就是 v1 的数；同会话重测的 A4 作旁证并排，不进判据
- **跑之前的闸与桩测**（11-08，协议批准前；`bash tests/run_tests.sh`，`logs/gate.txt`）：(a) 300 条合成流 11,800 项、(c) 3,600 项、(a′) 枚举对递推 600 项 + 枚举对引擎 9,000 项（15 个臂配置），错误都是 0；(v) 6 个追加配置分别在 128–285 / 300 条流上发生窗格内切换（其中 61–187 条另有边界切换）；(b) 1,152 次运行与 OPP 不一致 0；(c′) 10 份不一致 0；(e) 20 项不一致 0，v2 默认 B = 1024 时只有 Binance 触发（M、A2 各 1 次窗格内切换，切换总数仍是 1,027，与 v1 相同），其余 9 份触发 0 次、切换与压缩次数与 v1 逐项相同。v1 / v2 diff 只落在允许的块（`tests/diff_v1.py`）。代跑入口的端到端桩测 bash 3.2、bash 5.3 各 21 项全过（`tests/e2e_relay.sh`）。`run_e8.sh smoke` 只跑了判据之外的 4 格（E1 Nasdaq 留出 COUNT W = 5 分的 M / A2、E2 Porto X = 1.1 的 M、E5 S3 rw n = 10 有突发与 S1 rw n = 10⁴ k = 1 的 M），只核脚本跑通、列对、校验和与 v1 相同，产物在 `logs/`、不进任何报表；`compare_e8.py` 用 v1 的表冒充 v2 自测：(ii) 的判读与 v1 逐字相同、回归比值全是 1，重出的 E1 / E2 / E7 报表与原报表逐字节相同
- **机器时间估计**：本机 E1 的 M + A2 约 80 分钟、E2 约 40 分钟、E5 约 20 分钟（v1 里 M 慢的大格修好后变快）、E6 与旁证各几分钟，闸约 10 分钟 ⇒ 约 2.5–3 小时；工作站 E7 的 M 臂约 50 分钟 + 编译与闸约 5 分钟 ⇒ 约 1 小时
